11 · Local Development Plan

How we start building the database-free architecture (04): everything runs locally via docker-compose - MinIO stands in for S3, a Caddy static gateway stands in for CloudFront, and the baker processes data into artifacts. There is no database service to run, locally or ever; the cloud deployment is the same artifacts on real S3 behind a real CDN, config-only.

This document refines 04 Architecture and 10 Roadmap for the build-start phase. Where they conflict for local development, this document wins until MVP deploy planning begins.

Principles

DEV-1Local-first, cloud-shaped, database-freeMVP
  • One command up. make up gives a working stack: MinIO, static gateway, web dev server, plus a baked seed dataset. A new checkout reaches a browsable app in under 15 minutes (excluding large dump downloads).
  • MinIO is S3; the app speaks S3 everywhere. One aws-sdk-go-v2 code path in the baker; dev points at MinIO (S3_ENDPOINT, S3_FORCE_PATH_STYLE=true), cloud points at real S3. Never a code branch.
  • Caddy mimics CloudFront. A single dev entrypoint (localhost:8080) routes /v/* and /manifest.json to MinIO and / to the web app, and sets the immutable cache headers from ARCH-2 - so the client's URL contract is identical in dev and cloud.
  • No database, no API server. The serving path is static artifacts; the only compute is the baker, run as a job. DuckDB is embedded in the baker binary (and available as a CLI for ad-hoc analysis) - never a service.
  • Identical artifacts, parameterized environment. The same baker image and web build run in dev and cloud; the delta is env config and infra (Terraform: S3 + CloudFront instead of MinIO + Caddy). All configuration via env vars with a checked-in .env.example.

docker-compose stack

DEV-3Compose servicesMVP
# docker-compose.yml (shape, not final file)
services:
  minio:
    image: minio/minio
    command: server /data --console-address ":9001"
    environment:
      MINIO_ROOT_USER: wk
      MINIO_ROOT_PASSWORD: wk-dev-minio        # dev only
    ports: ["9000:9000", "9001:9001"]
    volumes: ["./data/minio:/data"]
    healthcheck: { test: ["CMD", "mc", "ready", "local"], interval: 3s }

  minio-init:                            # one-shot: create buckets, set
    image: minio/mc                      #   wk-artifacts anonymous-read, exit
    depends_on: { minio: { condition: service_healthy } }
    entrypoint: >-
      /bin/sh -c "mc alias set wk http://minio:9000 wk wk-dev-minio &&
                  mc mb -p wk/wk-dumps wk/wk-warm wk/wk-artifacts &&
                  mc anonymous set download wk/wk-artifacts"

  gateway:                               # CloudFront stand-in
    image: caddy:2
    volumes: ["./Caddyfile:/etc/caddy/Caddyfile:ro"]
    ports: ["8080:8080"]                 # /v/* + /manifest.json → minio,
    depends_on: [minio]                  # / → web; immutable cache headers

  web:
    build: ./web                         # vite dev server + source bind mount
    ports: ["5173:5173"]
    environment: { VITE_DATA_URL: http://localhost:8080 }

  baker:                                 # never long-running; invoked via
    build: .                             # `docker compose run baker `
    profiles: ["jobs"]
    environment:
      S3_ENDPOINT: http://minio:9000
      S3_FORCE_PATH_STYLE: "true"
      AWS_ACCESS_KEY_ID: wk
      AWS_SECRET_ACCESS_KEY: wk-dev-minio

volumes: {}
  • The dev loop is: edit seed/code → make bake (seconds at seed scale, per ARCH-4 incremental-bake) → browser refresh. A make bake-watch target re-bakes on seed/config change to keep ranking-tuning iteration tight.
  • The baker is a job, not a service: docker compose run baker bake --seed or natively go run ./cmd/baker bake --seed against the compose MinIO. Long dump jobs are resumable and report progress.
  • The gateway is the contract: the web app only ever talks to VITE_DATA_URL with the same paths CloudFront will serve. No dev-only URL shapes.

Because serving is static, "deploying" MVP to the cloud is: create buckets + CloudFront via Terraform, run the same bake + publish against real S3, upload the web build. Nothing else exists.

Data processing locally

DEV-5Local data pipelineMVP
  • Dumps land in wk-dumps (COLD): Wikidata JSON dump (start with the filtered/truthy variant, not the full ~100 GB dump), an OHM extract, Wikimedia pageview counts. make fetch-dumps downloads to ./data/staging/, verifies checksums, then mc-uploads; bake stages stream from S3 URLs so the same commands work against cloud buckets later.
  • Streaming, resumable ingest in Go (internal/ingest): bz2/gz stream → filter → normalize → validate → Parquet model tables in wk-warm (SRC-3). Rejects are data: reject Parquet + per-run report to s3://wk-warm/reports/.
  • Embedded DuckDB does the relational work over the Parquet model: joins, importance aggregation (ZOOM-2), census rollups (ROAD-2), bucket assignment - via checked-in SQL in internal/duck/sql/. The DuckDB CLI over the same files is the ad-hoc analysis tool.
  • Bake stages then materialize artifacts per ARCH-4 into wk-artifacts, finishing with an atomic manifest.json publish. Golden-view checks (ZOOM-5) run as part of bake and block publish on failure.
  • Seed set is first-class (SRC-8): checked-in NDJSON under data/seed/, split by domain (universe.ndjson, life.ndjson, civilizations.ndjson, science-tech.ndjson, culture.ndjson, future.ndjson, ...) plus manifest.json with seed_version, per-file counts, and sha256 checksums. NDJSON because seed entities need nested structure (temporal claims, properties with units and sources, inline GeoJSON) that CSV cannot express, git diffs stay line-per-entity reviewable, and lines flow through the same streaming ingest path as the dumps. Curation workflow: generate candidates per era via Wikidata SPARQL, hand-prune, commit.

Cloud deployment has no milestone here: after M6, Terraform the DEV-4 parity table (S3 + CloudFront), run the same bake against real buckets, upload the web build. No application changes.

Out of scope for this phase

  • No accounts/auth, no AI endpoints, no contributions - unchanged from 10.
  • No database of any kind (see ARCH-8 for the only sanctioned future exception), no Kubernetes, no LocalStack (MinIO covers all the S3 parity we need), no Kafka, no cache service.
  • No full Wikidata dump ingestion before the M6 gate passes.
