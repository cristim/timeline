11 · Local Development Plan

How we start building: everything runs locally via docker-compose for development speed - no CDN, no cloud accounts, data processed into local PostgreSQL and the local filesystem. Every choice below is made so the eventual cloud deployment (Aurora Serverless v2, S3, CloudFront, ECS) is a configuration swap, not a rewrite.

This document refines 04 Architecture and 10 Roadmap for the build-start phase. Where they conflict for local development, this document wins until MVP deploy planning begins.

Principles

DEV-1Local-first, cloud-shapedMVP
  • One command up. make up gives a working stack: database, API, frontend, seed data. A new checkout reaches a browsable app in under 15 minutes (excluding large dump downloads).
  • No CDN in dev, but the API still emits the Cache-Control/ETag/dataset-version headers from API-5 from day one, so CloudFront later fronts the same origin unchanged.
  • MinIO is the blob store: the app speaks S3 everywhere. One S3 client code path (aws-sdk-go-v2) in dev and in cloud; dumps, Parquet, and tiles live in MinIO buckets locally and in real S3 later. The difference is entirely env config: S3_ENDPOINT, credentials, S3_FORCE_PATH_STYLE=true for MinIO - never a code branch.
  • Postgres runs in compose next to the app and is the Aurora stand-in: same major version, Aurora-compatible extensions only (DEV-4). The app reaches it purely through DATABASE_URL.
  • Identical artifacts, parameterized environment. The same container images and application code run in dev and in cloud; dev vs. cloud differs only at the infra level (compose file vs. Terraform: Aurora endpoint instead of the db container, S3 endpoint instead of MinIO, CloudFront in front). All configuration via env vars with a checked-in .env.example; the same variables map 1:1 to ECS task definitions.

One Go module, two binaries. No separate services until a measured need exists (ARCH-1 non-deployments apply to dev too).

Data access: pgx + sqlc, no ORM. Queries are checked-in SQL files; sqlc generates typed Go from them. This keeps every hot-path query visible for the EXPLAIN gates in DEV-4 and CI. Migrations via golang-migrate, embedded in the binaries.

docker-compose stack

DEV-3Compose services and profilesMVP
# docker-compose.yml (shape, not final file)
services:
  db:
    image: postgis/postgis:16-3.4        # match Aurora PG major version
    environment:
      POSTGRES_DB: worldknowledge
      POSTGRES_USER: wk
      POSTGRES_PASSWORD: wk-dev          # dev only
    ports: ["5432:5432"]
    volumes:
      - pgdata:/var/lib/postgresql/data
    command: >-                          # dev-tuned for bulk imports
      postgres -c shared_buffers=1GB -c maintenance_work_mem=1GB
               -c max_wal_size=4GB -c synchronous_commit=off
    healthcheck: { test: ["CMD-SHELL", "pg_isready -U wk"], interval: 3s }

  minio:
    image: minio/minio
    command: server /data --console-address ":9001"
    environment:
      MINIO_ROOT_USER: wk
      MINIO_ROOT_PASSWORD: wk-dev-minio        # dev only
    ports: ["9000:9000", "9001:9001"]
    volumes: ["./data/minio:/data"]
    healthcheck: { test: ["CMD", "mc", "ready", "local"], interval: 3s }

  minio-init:                            # one-shot: create buckets, then exit
    image: minio/mc
    depends_on: { minio: { condition: service_healthy } }
    entrypoint: >-
      /bin/sh -c "mc alias set wk http://minio:9000 wk wk-dev-minio &&
                  mc mb -p wk/wk-dumps wk/wk-warm wk/wk-tiles wk/wk-basemap"

  api:
    build: { context: ., target: api }   # air hot-reload + source bind mount in dev
    environment:
      DATABASE_URL: postgres://wk:wk-dev@db:5432/worldknowledge
      S3_ENDPOINT: http://minio:9000
      S3_FORCE_PATH_STYLE: "true"
      AWS_ACCESS_KEY_ID: wk
      AWS_SECRET_ACCESS_KEY: wk-dev-minio
      DATASET_VERSION: dev
    ports: ["8080:8080"]
    depends_on:
      db: { condition: service_healthy }
      minio: { condition: service_healthy }

  web:
    build: ./web                         # vite dev server + source bind mount
    ports: ["5173:5173"]
    environment: { VITE_API_URL: http://localhost:8080 }

  importer:                              # never long-running; invoked via
    build: { context: ., target: importer }   # `docker compose run importer `
    profiles: ["jobs"]
    environment: *same-env-as-api        # anchor in the real file

volumes: { pgdata: }
  • Everything runs in compose: db, minio, api, and web come up together with make up. Hot reload stays fast via bind mounts (air for Go, Vite's own watcher for the frontend); running a binary natively against the compose db/minio remains a personal escape hatch, not the documented flow.
  • The app is 12-factor parameterized: the api/importer containers know nothing about "dev vs cloud" - they read DATABASE_URL and the S3_*/AWS_* variables. Pointing those at Aurora and real S3 (dropping S3_ENDPOINT/path-style) is the entire deployment delta; no code changes, only infra.
  • Importer is a job, not a service: docker compose run importer import-wikidata --dump s3://wk-dumps/.... Long dump processing runs are resumable and write progress to stdout + a state row.
  • The dev Postgres flags trade durability for import speed; they are dev-only and must never appear in cloud parameter groups.
  • Makefile is the interface: make up / down / migrate / seed / import-census / test / smoke / psql.

Cloud parity rules

DEV-4Aurora Serverless v2 compatibility guardrailsMVP

Target production database: Aurora PostgreSQL Serverless v2. Everything built locally must stay inside its envelope:

RuleWhy
Pin Postgres major version to one Aurora currently offers (16.x); record it in .env.example and CI.No surprise SQL/planner differences at migration time.
Extensions allowlist: postgis, pg_trgm, btree_gist, pg_stat_statements only. Adding any extension requires checking Aurora's supported-extensions list first and noting it here.Aurora rejects unsupported extensions; discovering that at deploy time is a rewrite risk.
No superuser assumptions, no COPY FROM PROGRAM, no server filesystem access, no FDWs, no custom tablespaces, no logical-replication tricks.Not available on managed Postgres.
Bulk loads use client-driven COPY FROM STDIN from the importer.Works identically against local Postgres and Aurora.
Schema + queries assume nothing about instance-local caching; heavy read paths must be coverable by indexes (test with EXPLAIN gates in CI).Serverless v2 capacity scales with load; unindexed scans translate directly into ACU cost.
Connection handling via a small pool (pgx pool, max ~10 in dev); keep the API pool-friendly so RDS Proxy can be inserted later if Lambda-style scaling is ever used.Aurora connection limits scale with ACU.

Data processing locally

DEV-5Local data pipelineMVP
  • Dumps land in the wk-dumps bucket (COLD): Wikidata JSON dump (start with the filtered/truthy variant, not the full ~100 GB dump), an OHM extract, Wikimedia pageview counts. make fetch-dumps downloads to ./data/staging/, verifies checksums, then mc-uploads into MinIO; importers stream from S3 URLs so the same commands work against cloud buckets later.
  • Streaming, resumable importers in Go (internal/ingest): bz2/gz stream → line-delimited JSON → filter → normalize → validate → COPY into staging → atomic swap (SRC-3 unchanged). A full local Wikidata pass is an hours-scale batch job; progress reporting and resume-from-offset are requirements, not nice-to-haves.
  • Rejects are data: reject tables + a per-run import report written to s3://wk-warm/reports/.
  • DuckDB as the local analytics sidecar (CLI, not a service): ad-hoc queries over Parquet outputs, census report generation (ROAD-2), and JSON→Parquet transforms where Go code isn't worth writing. Anything DuckDB produces that the product needs must still be reproducible via make targets.
  • Precompute jobs run as importer subcommands: rank (ZOOM-2), bucketize (ZOOM-3), build-chunks (timeline chunks to wk-tiles). Output tables carry the dataset version stamp.
  • Seed set is first-class (SRC-8): the Phase-0 curated set is checked-in NDJSON (one entity per line) under data/seed/, split by domain (universe.ndjson, life.ndjson, civilizations.ndjson, science-tech.ndjson, culture.ndjson, future.ndjson, ...) plus a manifest.json with seed_version, per-file entity counts, and sha256 checksums. NDJSON wins over CSV/Parquet here because seed entities need nested structure (temporal claims, properties with units and sources, inline GeoJSON geometry) that CSV cannot express, git diffs stay line-per-entity reviewable, and the lines flow through the same streaming ingest path as the Wikidata dumps. Curation workflow: generate candidates per era via Wikidata SPARQL, hand-prune, commit.

Cloud deployment intentionally has no milestone here: it begins only after M6 passes, as Terraform for the parity table in DEV-4 (Aurora Serverless v2, S3, CloudFront, ECS), and should change no application code beyond env vars and the blob.S3 implementation.

Out of scope for this phase

  • No accounts/auth, no AI endpoints, no contributions - unchanged from 10.
  • No Kubernetes, no LocalStack (MinIO covers all the S3 parity we need), no Kafka, no cache layer (the DB is fast enough at seed scale; caching design stays header-level per DEV-1).
  • No tile pregeneration pipeline (dynamic tiles suffice at local scale).
  • No full Wikidata dump ingestion before the M6 gate passes.
