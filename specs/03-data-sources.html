03 · Data Sources & Ingestion

We do not build a historical dataset from zero. Machines provide breadth; our intellectual work is classification, importance ranking, relationships, and semantic zoom.

Never import a competitor's derived database (ChronoAtlas polygons, Chronas cleaned data) without verifying their license explicitly. Using the same upstream source is fine; copying their resulting database is not. Their cleaning/ranking work is itself protectable value. Before commercial launch, have a lawyer review the Wikipedia fact-extraction method (EU database rights).
SRC-2Provenance on every recordMVP

Every imported claim/geometry/media row carries source, source_id, license, attribution, source_url, retrieved_at (DM-9). The pipeline automatically applies attribution in the UI and can exclude by license. A record arriving without resolvable license is a hard ingestion error, not a default to "assume fine".

Ingestion pipeline

SRC-3Importer architectureMVP
S3 (raw dumps: wikidata json.bz2, OHM pbf, commons metadata)
   │  versioned, immutable - COLD tier
   ▼
baker ingest stages (Go + embedded DuckDB, batch, idempotent, resumable)
   ├── parse + filter        (entity type allowlist, quality gates)
   ├── normalize             (to DM-* logical schema; unit + calendar normalization)
   ├── entity resolution     (wikidata_id is the join key; OHM wikidata tags)
   ├── validate              (schema, coordinate sanity, date sanity - fail loud,
   │                          write rejects to reject Parquet with reason)
   ├── classify              (category facets from instance_of/subclass trees)
   ├── rank                  (importance vector - see 07 ZOOM-2)
   └── write                 (versioned Parquet model tables in wk-warm)
   ▼
WARM tier: Parquet model + full candidate sets (papers, patents) in wk-warm
HOT  tier: baked serving artifacts in wk-artifacts (chunks, entity docs,
           PMTiles, search shards - see ARCH-4), published atomically via
           the dataset manifest
  • Bakes are reproducible: same dump + same code → byte-identical artifacts (modulo compression). Every run records dump version and counts (parsed / accepted / rejected per reason).
  • A re-bake is a new dataset version + manifest repoint, never in-place mutation. When user contributions exist later, they are an additional input NDJSON stream to the bake (ARCH-8), not writes to a live store.
  • Wikidata extraction pulls at minimum: labels, descriptions, instance_of/subclass_of, P580/P582/P585 (times), P625 (coords), P276 (location), P710 (participant), P361 (part of), P828/P1542 (cause/effect), P61/P575 (discovery), sitelinks, image (P18), Commons category.
SRC-4Wikipedia fine-detail extractionV2

LLM extraction jobs turn Wikipedia sections into structured sub-events (JFK timeline at minute precision, D-Day landings by hour). Each extracted record retains the source paragraph reference, gets value_type=estimated-equivalent status and a confidence score, and is never treated as automatically true. MVP only stores Wikipedia links; the extraction pipeline is V2 and feeds buckets T11–T13.

SRC-6Papers, patents, books: metadata onlyMVP (seed)
paper  { doi, title, authors, publication_date, venue,
         abstract_if_permitted, citation_count, topics, related_entities }
patent { patent_id, office, filed, published, granted, assignee,
         inventors, citations, related_entities }

Full text is out of scope permanently (changes the project completely). MVP seeds ~100k landmark papers/patents chosen by citation count + links to HOT entities; the rest stays WARM.

SRC-7Media curationMVP

Commons: pick per-entity hero image from P18 + category heuristics; store license/author/attribution per file. YouTube: an offline curation job (search + metadata + manual allowlist for the top ~2k entities) produces ranked media_ref rows; the client embeds the player. No live YouTube search in the view path.

SRC-8Time series and deep-time dataMVP (seed)

Curated small series (world population, CO₂, life expectancy, transistor count, record speeds/heights) enter property_value directly. Large/dense series go to Parquet with a manifest entity in the DB. Deep-time content (geological periods, paleogeography, evolution milestones, future projections) is a hand-curated seed dataset (~2–5k entities) assembled from Wikidata + NASA + literature, because Wikidata alone is thin there. This seed set is what makes Big Bang → future browsing work at all and is a Phase-0 deliverable (ROAD-1).

Validation gates (fail loud)

  • Dates: entity lifetimes must be internally consistent (birth < death; part_of child within parent range ± tolerance) - violations go to the reject table.
  • Coordinates: located-in country vs. coordinates cross-check ("battle in Germany, coords in Brazil" → reject/flag).
  • Outliers: property values >5σ from type cohort flagged (T. rex at 800 t).
  • Duplicates: same wikidata_id twice is fatal; near-name+near-time+near-place pairs flagged for review.
  • Every gate emits counts to the import report; a >2% reject-rate jump between dump versions fails the run for human review.
