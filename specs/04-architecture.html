04 · System Architecture

Static-first and database-free: a build-time baker turns source dumps into a versioned set of static artifacts on object storage, and clients query those artifacts directly. No database server exists in the serving path - or anywhere else. Historical content is read-heavy and immutable per dataset version; this architecture is that fact, taken literally.

Topology

ARCH-1Static serving, batch bakingMVP
SERVING (no servers of ours at all)
                     CDN (CloudFront; Caddy in dev)
                             │
              S3 / MinIO artifact buckets
      ┌──────────┬───────────┼────────────┬─────────────┐
   web app   entity docs   viewport    layer tiles   search shards,
  (static)     (JSON)    chunks (JSON) (PMTiles)     Parquet, snapshots

BUILD (batch job, run per dataset version)
   dumps (wk-dumps bucket)
        │
      baker  =  Go binary + embedded DuckDB (library, not a service)
        │       + tippecanoe for tile generation
        ▼
   artifacts (wk-artifacts bucket, path-versioned /v/<dataset>/...)
  • The baker is the only compute we own: parse → normalize → validate → rank → bucketize → bake artifacts. DuckDB runs embedded inside the baker process for joins, aggregation, and Parquet I/O - a query library like SQLite, not a database service. The artifacts and the source dumps are the only state anywhere.
  • Clients resolve every read themselves: they compute artifact keys from view state (API-1), fetch entity docs by slug, read tile byte-ranges from PMTiles, and run analytics over Parquet with DuckDB-Wasm (ARCH-7). "The API" is a URL contract over static objects, not a process.
  • Explicit non-deployments (each requires a measured justification to add later): any database server (PostgreSQL included), Kubernetes, Kafka/queues, graph DBs, Elasticsearch, application servers on the anonymous read path, embeddings infra, microservices.
  • The one place a database is allowed to return is ARCH-8.
  • Host-agnostic by construction: the serving contract is only "static hosting + object storage with HTTP range requests + CORS". CloudFront+S3 is one instantiation; Cloudflare is another: Pages (or Workers static assets) hosts the app shell, and the artifact buckets live in R2 behind the Cloudflare CDN. R2 is S3-compatible, so the baker's S3 client and the MinIO dev setup cover it unchanged via S3_ENDPOINT; R2's zero-egress pricing improves ARCH-5 further. Artifacts must not live inside a Pages deployment itself: Pages' per-file (~25 MiB) and file-count (~20k) limits rule out PMTiles archives, Parquet, and per-slug docs at MVP scale - Pages serves the shell, R2 serves the data.

Caching and versioning

ARCH-2Immutable, path-versioned artifactsMVP
  • Every artifact lives under /v/<dataset>/... and is immutable: Cache-Control: public, max-age=31536000, immutable. A dataset release is a pointer flip (the app loads a tiny mutable /manifest.json naming the current dataset version), never a purge.
  • CDN hit rate stops being a tuning problem: every object is cacheable forever by construction. The 100,000th viewer of "Roman Empire, 117 CE" costs a CDN hit; the first costs one S3 read.
  • Rollback = repoint the manifest at the previous dataset version, which still exists in full.
  • Old dataset versions are garbage-collected on a fixed retention (keep last N releases); deleting a released version is a destructive op and gets the corresponding care.

Geometry delivery

ARCH-3PMTiles archives, range requests, no tile serverMVP
  • Each map layer × time-step is baked (tippecanoe) into a single PMTiles archive: /v/<dataset>/layers/<layer>/<timestep>.pmtiles. MapLibre's pmtiles protocol reads the embedded index over HTTP range requests and fetches only the byte ranges the viewport needs - client-side spatial querying against S3, no tile server.
  • Time quantization keeps the archive set finite: time-steps follow data density (century steps before 1000 CE, decade 1000-1900, year after 1900; config, not code). The client snaps the time cursor to the nearest step.
  • Basemap: protomaps .pmtiles (OSM-derived), same mechanism, own attribution (FE-9). Deep-time paleogeography basemaps are additional pmtiles sets keyed by geological time (FE-5).
  • FlatGeobuf is the designated alternative for feature-level layers if PMTiles granularity is ever wrong; both are range-request formats, so swapping stays inside the layer loader.

The bake pipeline

ARCH-4Bake stages and artifact catalogMVP

One bake run per dataset version produces, in order (each stage resumable and reproducible from dumps + code per SRC-3):

StageArtifactSpec
ingest + validatenormalized entity/claim/geometry Parquet tables in wk-warm (the working model), reject tables, import reportSRC-3, DM-*
rankimportance vectors joined onto entitiesZOOM-2
bucketizebucket_min/bucket_max per entityZOOM-3
bake chunksviewport chunk JSON per (bucket × time-window × tile × category) - the ranking function runs here, at bake timeZOOM-4, API-1
bake entitiesone JSON doc per slug, aliases.json (DM-2a), SSG HTML entity pages for SEOAPI-2, API-6
bake tilesPMTiles per layer/time-stepARCH-3
bake searchprefix-sharded search index JSONSRCH-1
bake analyticssorted/partitioned Parquet for DuckDB-Wasm; "world at date" snapshotsARCH-7, VIS-5
publishmanifest.json (dataset version, checksums, counts, golden-view results) - written last, atomicallyARCH-2, ZOOM-5
  • Incremental bake is a requirement, not an optimization: artifacts are content-hashed and unchanged objects are not re-uploaded. At seed scale a full bake takes seconds (which keeps the ranking-tuning loop fast); at millions of entities the first bake is hours and every subsequent bake must be proportional to the delta.
  • Category combinatorics: chunks are baked per single category plus one "all" tier; the client unions selected categories and applies the importance slider locally. Never bake the 2^n category subsets.
  • Entities spanning multiple time-windows are duplicated into every chunk they overlap - denormalization is free when storage is the only cost.

  • The AI cost fence (SRCH-4) is unchanged and remains the only per-user variable cost when V2 AI features arrive.

Operational requirements

ARCH-6Ops baseline for a static systemMVP
  • No backup problem: source dumps + baker code reproduce everything, and released artifact versions are themselves immutable snapshots. Protect the dumps bucket and the repo; that is the entire disaster-recovery story.
  • Every bake writes a report (counts, rejects, checksums, golden-view results per ZOOM-5). Publishing a manifest whose golden views fail is a blocked release, not a warning.
  • Observability: CDN/S3 access logs + client-side error reporting. There is no server to page on.
  • The dataset version is stamped into the manifest and every page footer.
  • Security surface: artifacts public-read, dumps private, signed publish credentials for the baker, WAF at the CDN. No injection surface exists because no server of ours parses queries.

Client-side analytics

ARCH-7DuckDB-Wasm over ParquetV2

Charts/Compare/records-over-time query the baked Parquet directly in the browser: DuckDB-Wasm reads row-group statistics over HTTP range requests and fetches only the byte ranges the query needs. The bake sorts/partitions Parquet by (bucket, time, region/geohash) so predicate pushdown prunes effectively. This is the right tool for analytics questions and the wrong tool for the 60 fps pan/zoom loop - the chunk/PMTiles path (ARCH-3/4) owns interactive rendering.

Database contingency

ARCH-8Where a database is allowed to returnLATER

The knowledge graph never moves into a database: it is baked, versioned, and served static, permanently. A database may be added only for genuinely dynamic state, none of which exists in MVP: user accounts, saved views, contribution queues (09), or a server-side search upgrade if static shards hit a quality ceiling (SRCH-1). When that day comes, it is a small Aurora Serverless v2 PostgreSQL holding user data only, sized like an ordinary SaaS user store - and contributions still flow into the bake, never into the serving path. Guardrails for that future store: pin a supported PG major version, extensions allowlist (pg_trgm, btree_gist), no superuser assumptions, client-driven COPY.
