04 · System Architecture

Deliberately boring: Go + PostgreSQL/PostGIS + S3 + CloudFront + vector tiles. Historical content is read-heavy, immutable, and cacheable; exploit that everywhere.

Stack: CloudFront + S3 + ALB/API Gateway + ECS (or Lambda) + RDS PostgreSQL with PostGIS. Infrastructure as Terraform. Single region.

Explicit non-deployments (each requires a measured justification to add later): Kubernetes, Kafka/queues, Neo4j/graph DB, multiple databases, Elasticsearch (until search outgrows Postgres, see SRCH-2), embeddings infra, microservices. One Go binary for the API, one for the importer.

Caching: the economic core

ARCH-295%+ of browsing served from CDNMVP

Ancient Rome will not change tomorrow. The 100,000th viewer of "Roman Empire, 117 CE" must cost approximately nothing.

  • All GET API responses carry Cache-Control: public with long TTLs + ETag derived from dataset version. Viewport queries are cacheable because their inputs are quantized (API-1 snaps time ranges and bboxes to a grid).
  • Tiles, timeline chunks, entity summaries, thumbnails: cached at edge, invalidated only by dataset version bump (path-versioned: /v/2026-08/... so invalidation is a pointer flip, not a purge).
  • Dynamic compute is reserved for: search-as-you-type, logged-in features, AI.
  • Target: CDN hit rate >95% for anonymous browsing. Measured from day one; a dashboard widget, not an aspiration.

Geometry delivery

ARCH-3Vector tiles, never GeoJSON floodsMVP

Historical geometry ships as Mapbox Vector Tiles: /tiles/{layer}/{z}/{x}/{y}?time=117. Never send the Roman Empire's polygon coordinates through the REST API on every map move.

  • Time quantization: tiles are generated per time-step, not per year. Steps follow data density: e.g. century steps before 1000 CE, decade steps 1000–1900, year steps after 1900. The tile URL time parameter snaps to the nearest step, keeping the tile set finite and cacheable.
  • MVP pregenerates tiles for the border/territory layer from OHM data at agreed steps; a dynamic tile server (PostGIS ST_AsMVT) covers long-tail layers, fronted by the CDN.
  • Basemap: MapLibre-compatible open vector basemap (e.g. OpenMapTiles-based, self-hosted or provider) - not Google Maps; we need full control over historical overlays.
  • Deep-time paleogeography basemaps are separate raster/vector tile sets keyed by geological time (FE-5).

  • AI spend is fenced by policy (SRCH-4): naive LLM-per-interaction at 1M MAU would cost ~$100k/mo and is forbidden.

Operational requirements

ARCH-6Ops baselineMVP
  • Backups: automated RDS snapshots + weekly logical dump to S3; restore path tested before launch.
  • Observability: structured logs, RED metrics per endpoint, slow-query log; p95 targets in API-5.
  • Deploys: CI-built images, staging environment, migrations via versioned files (golang-migrate or equivalent), reversible.
  • The dataset version (dump + pipeline git SHA) is exposed at /api/version and stamped into every page footer.
  • Security: no PII in MVP beyond optional accounts (V2); secrets in SSM/Secrets Manager; WAF via CloudFront.
