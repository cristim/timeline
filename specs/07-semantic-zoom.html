07 · Semantic Zoom & Ranking

The hard and interesting problem: which 50 things should appear out of 5 million, at this exact time scale, geographic scale, and topic filter? If this ranking works, the product works. Everything here is precomputed; rendering must be cheap.

The mechanic

ZOOM-1Zoom changes the information hierarchy, not just the scaleMVP

Simultaneously, geographic zoom shifts which importance dimension applies: world view uses global importance; zoom into Germany blends national importance; zoom into Berlin surfaces local history that would never appear at world scale. Europe+1500–1600 must not surface Japanese village events.

Precomputed importance

ZOOM-2Importance vector per entityMVP
importance (jsonb on entity):
{
  "global":   0.97,
  "region":   { "DE": 0.99, "EU": 0.98 },     -- sparse, top regions only
  "category": { "war": 0.99 },
  "quality":  0.9                             -- data completeness score
}

MVP scoring function (deterministic, computed at import; weights in config, not code):

global = w1 * norm(log(wikipedia_sitelink_count))
       + w2 * norm(log(wikipedia_pageviews_1y))     -- from Wikimedia pageview dumps
       + w3 * norm(log(1 + inbound_wikidata_refs))
       + w4 * type_prior                            -- e.g. states > minor sports events
region[r] = blend(global, locality(r))              -- entities located in r get a
                                                    -- regional boost so local history
                                                    -- surfaces at local zoom
  • Scores are floats 0..1, comparable only within the same dataset version.
  • The scoring job emits a ranked sample report (top 100 per bucket) on every run; eyeballing that report is part of import review.
  • V2: crowd pairwise voting ("which is more important: first powered flight vs. founding of company X") feeds a contextual Elo-style adjustment (CONTRIB-6). The storage shape already supports it.

Each entity gets bucket_min/bucket_max: the range of buckets where it is a sensible render candidate. Examples: Big Bang T0–T4 · Roman Empire T5–T9 · WWII T6–T10 · D-Day T8–T12 · Omaha Beach assault T10–T13.

Assignment rule (import-time):

bucket_min = coarsest bucket where the entity ranks in the top N of its
             time-window at its importance level (N per bucket, config)
bucket_max = finest bucket justified by its time_precision
             (a day-precision battle: T13; a million-year species: T8)

The client's continuous zoom maps to a bucket via visible-range thresholds; crossing a threshold loads the adjacent bucket's data (prefetched, crossfaded - FE-2).

The ranking function

ZOOM-4relevance() for chunk bakingMVP
relevance(entity, view) =
    base importance for view scope
        world view:            importance.global
        region/country view:   max(importance.global * 0.8,
                                   importance.region[view.region])
  * category boost   (entity.category in view.cat ? 1 : 0 when filtered)
  * overlap factor   (fraction of [t0,t1] the entity overlaps; full-span
                      background entities like "Roman Empire" at T9 get a
                      floor so context bands don't vanish)
  * quality factor   (importance.quality, floor 0.5)
  • Runs entirely at bake time (the "bake chunks" stage, ARCH-4): DuckDB SQL over the Parquet model + a Go re-rank per chunk, writing the top-N per (bucket × window × tile × category). Nothing scores at view time; the client only unions chunks and applies the importance slider locally.
  • Deterministic: same inputs → same chunk contents, stable ordering (ties broken by slug) - required for reproducible bakes and content-hash incrementality (ARCH-4).
  • Diversity guard: at most K items per category per screen at coarse buckets (config), so 1942 doesn't render as 300 battles and nothing else.

Acceptance criteria

ZOOM-5Golden-view testsMVP

A checked-in suite of golden viewport queries with expected inclusions/exclusions, run against every dataset build (data regression tests, not unit tests). Each golden-view expectation file pins the seed_version / dataset version it was written against, so a data change that breaks a view shows up as an explicit expectation diff to review, never as flakiness:

  • Whole-universe view (T0): shows Big Bang, galaxy formation, Sun/Earth formation, first life, Cambrian explosion, dinosaurs, extinction, humans, NOW, red-giant future - between 15 and 30 items total.
  • World + T8 (century) at 1900–2000: WWI, WWII, Moon landing, Internet present; no local festivals.
  • Europe + T10 (year) at 1942: Stalingrad present; Pacific-only events absent unless global-tier.
  • Berlin + T10 at 1942: local Berlin events present that the Europe view did not show.
  • Kyoto + 1500–1600 at T9: Japanese history dense; European events only global-tier.
  • Category filter "science" at T8, 1850–1950: relativity, quantum theory, penicillin, DNA precursors; no battles.
  • Every view resolves from ≤ 15 chunk fetches, each ≤ 64 KB gz (API-5 budgets).

The suite runs inside the bake stage against the baked chunks and blocks publish on failure (ARCH-6). These views double as the Phase-0 demo script (ROAD-1).

Design guard: resist making ranking "smart" early. A transparent, debuggable formula over sitelinks+pageviews+type priors, plus hand-tuned per-bucket caps, beats an opaque model while the product is finding its shape. Crowd ranking and learned ranking are V2+ refinements over the same stored shape.
