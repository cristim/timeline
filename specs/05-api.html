05 · Read Contract

There is no query server: "the API" is a contract of static artifact URLs under /v/<dataset>/ plus the client-side rules for computing them (ARCH-1). The viewport chunk-key scheme is the product's most important interface - arguably more important than the UI itself. Everything is immutable and CDN-cached forever (ARCH-2).

Bootstrap

API-0GET /manifest.jsonMVP
GET /manifest.json               -- the ONLY mutable object
{
  "dataset": "2026-08",          -- everything else lives under /v/2026-08/...
  "basemap": {
    "key": "basemap/protomaps-20260829-z0-6.pmtiles",
    "source": "https://build.protomaps.com/20260829.pmtiles",
    "attribution": "<a href=\"https://github.com/protomaps/basemaps\">Protomaps</a> · © <a href=\"https://www.openstreetmap.org/copyright\">OpenStreetMap contributors</a> · <a href=\"https://docs.overturemaps.org/attribution/\">© ESA WorldCover project 2020 / Contains modified Copernicus Sentinel data (2020) processed by ESA WorldCover consortium</a> (<a href=\"https://creativecommons.org/licenses/by/4.0/\">CC BY 4.0</a>)",
    "sha256": "91578880b31e965f7e1c27c3efe1e2f53bb60e87b758349761a5f32cbb37b675"
  },
  "buckets":  { "T9": { "window_s": ..., "grid_epoch": ... }, ... },
  "timesteps": { "borders": [ ... ] },     -- snapped tile time-steps (ARCH-3)
  "categories": [ "war", "politics", ... ],
  "layers": [ ... ], "counts": { ... }, "seed_version": "...", "checksums": "..."
}

The client loads this once; every subsequent key is computed locally from it. A dataset release is a manifest repoint (ARCH-2); rollback likewise.

basemap is required. Its key is relative to /v/<dataset>/ and is derived from the verified source filename. The archive is immutable, served as application/vnd.pmtiles, and remains outside layers and timesteps because it is not a time-sliced overlay. The source, SHA-256, and complete HTML attribution travel with the descriptor so clients can verify and credit the exact archive they render.

The viewport chunks

API-1Client-computed chunk keysMVP
/v/<dataset>/chunks/<tb>/<window>/<tile>/<category>.json

  tb        time bucket in view (T0..T13, ZOOM-3)
  window    time window index: floor(t / bucket_window_seconds), from the
            manifest grid - the client snaps its continuous view to it
  tile      map tile address z/x/y at the bucket's configured zoom,
            or "world" for global views
  category  ONE category, or "all" (top tier across categories)

The client derives every key itself: snap the visible time range to window indexes, snap the bbox to tile addresses, fetch the needed (window × tile) chunks for each selected category, union, dedupe by slug, apply the importance slider locally, render. That is the entire "query engine". Chunk content (ranking baked per ZOOM-4):

{
  "items": [
    {
      "slug": "battle-of-waterloo", "type": "event",
      "name": "Battle of Waterloo",
      "t0": "1815-06-18", "t1": "1815-06-18", "precision": "day",
      "status": "documented",
      "point": [4.41, 50.68],          // render anchor; full geometry via PMTiles
      "categories": ["war"],
      "importance": 0.97,
      "media_thumb": "https://...",
      "child_count": 6                  // sub-events exist at deeper buckets
    }, ...
  ]
}
  • Bounded by construction: each chunk holds at most N items (per-bucket cap from ZOOM-4, including the diversity guard); entities spanning windows are duplicated into every window they overlap (ARCH-4). A view unions a handful of chunks, never the dataset.
  • Empty is a file: windows/tiles with no qualifying entities bake as an empty {"items":[]} chunk. A 404 on a manifest-valid key is a bake bug, not a normal condition; the client reports it.
  • Size budget: p95 chunk ≤ 64 KB gzipped; fetch p95 < 30 ms through the local gateway (DEV-6 M2).

  "description": "...",
  "temporal": { "t0": "-68e6y", "t1": "-66e6y", "precision": "million_year",

  "properties": [
    { "property": "mass", "synthesis": { "min": 8000, "max": 10200, "unit": "kg" },
      "claims": [
        { "value": {"min":8000,"max":9500}, "unit":"kg", "value_type":"estimated",
          "method":"volumetric model", "published_at":"2011",
          "source": { "kind":"paper", "title":"...", "url":"..." }, "confidence":0.7 },
        ...                              // full claim history incl. superseded -
      ] }                                // powers "estimates over time" (FE-6)
  ],
  "relationships": [
    { "type": "parent_taxon", "target": {"slug":"tyrannosauridae", "name":"..."} },
    { "type": "contemporary_with", "target": {"slug":"triceratops", "name":"..."} }
  ],
  "contemporaries": [ ... top 50, precomputed ... ],
  "children": [ ... part_of tree, one level ... ],
  "geometry_summary": { "kind": "point_distribution", "layer": "fossils" },
  "media": [ {kind, thumbnail_url, attribution, ...} ],
  "links": { "wikipedia": "...", "wikidata": "Q14332" },
  "sources": [ ... ]
}

One self-contained document per entity - claims, precomputed contemporaries, and the immediate part_of tree are inlined rather than sub-resources, because there is no server to compose them. Slug aliases resolve via /v/<dataset>/aliases.json (DM-2a) client-side; the future CDN can additionally emit real 301s from it.

API-3ComparisonMVP

Compare is a pure client computation over two entity documents: align shared properties from the property_def registry (shipped in the manifest), convert units to canonical, flag measured vs. estimated, compute temporal overlap ("did these coexist?"). No endpoint exists. MVP: 2 entities; V2: n entities + chart series via the Parquet/DuckDB-Wasm path (ARCH-7).

     time cursor to the manifest's timestep list; MapLibre pmtiles protocol

     client-side matching, no search server

Cross-cutting contract

API-5Conventions and budgetsMVP
  • All artifacts under /v/<dataset>/: immutable, Cache-Control: public, max-age=31536000, immutable. /manifest.json: max-age=60, must-revalidate. Set by the gateway/CDN (DEV-1), identical in dev and cloud.
  • Time values on the wire: ISO-8601 where in range; otherwise {"y": -6.6e7} year offsets; one serializer/deserializer shared between baker (Go) and client (TS) via generated types.
  • Key computation is a shared, tested library: the same quantization code (or a transpiled/ golden-tested twin) runs in the baker when writing keys and in the client when computing them - a drift between the two is the failure mode of this architecture, so it gets its own test suite.
  • Slugs are the public identity; internal ids never appear in artifacts (DM-2a).
  • Budgets: chunk ≤ 64 KB gz p95; entity doc ≤ 128 KB gz p95; search shard ≤ 256 KB gz; first meaningful view ≤ 15 artifact fetches.
  • Public data productization (bulk export, API keys) is LATER - trivially, since the artifacts and Parquet are already downloadable objects.

Shareable URL scheme (app routes, static HTML shells for SEO)

API-6Every view state has a URLMVP
/time/1945-04-30/map/berlin?layers=war,politics      -- date + place view
/time/-66000000/world                                 -- deep time
/entity/tyrannosaurus-rex                             -- entity page
/entity/trex?compare=african-elephant                 -- comparison
/time/1900/records                                    -- V2: records at date
/history/france/1800-1900                             -- V2: generated SEO pages
/inventions/19th-century                              -- V2: generated SEO pages

Rules: URLs are the sharing/education/SEO engine. Canonical entity pages (/entity/{slug}) are baked as static HTML (title, description, key facts, attribution) at bake time - SSG, not SSR - and the app hydrates on top. Generated intersection pages (time × place × category) are V2 outputs of the snapshot bake stage (ARCH-4).
