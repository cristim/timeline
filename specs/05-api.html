05 · API

The viewport query is the product's most important interface - arguably more important than the UI itself. Everything is JSON over HTTPS, versioned under /api/v1, aggressively cacheable.

The viewport query

API-1GET /api/v1/viewportMVP
GET /api/v1/viewport
    ?t0=-0631152000            & t1=-0442800000     -- timeline_time (seconds, scientific
                                                       notation allowed: t0=-2.08e17)
    & bbox=5.0,40.0,30.0,60.0                       -- lon/lat, optional (absent = whole world)
    & tb=T9                                          -- time bucket in view (T0..T13)
    & z=6                                            -- map zoom, optional
    & cat=war,politics                               -- category filter, optional
    & limit=300                                      -- server clamps to <= 500

Returns the 100–500 most renderable objects for that view - never the full dataset:

{
  "dataset": "2026-08",
  "items": [
    {
      "id": 48314, "slug": "battle-of-waterloo", "type": "event",
      "name": "Battle of Waterloo",
      "t0": "1815-06-18", "t1": "1815-06-18", "precision": "day",
      "status": "documented",
      "point": [4.41, 50.68],          // render anchor; full geometry via tiles
      "categories": ["war"],
      "importance": 0.97,
      "media_thumb": "https://...",
      "child_count": 6                  // sub-events available at deeper buckets
    }, ...
  ],
  "clusters": [ ... ]                   // optional server-side clusters when limit hit
}

Server-side semantics (ranking function itself is ZOOM-4):

WHERE entity time range overlaps [t0,t1]
  AND (bbox IS NULL OR geometry && bbox)
  AND tb BETWEEN bucket_min AND bucket_max
  AND categories && cat
ORDER BY relevance(importance, viewport) DESC
LIMIT clamp(limit)
  • Quantization for cacheability: the server snaps t0/t1 to the bucket's grid and bbox to the map-tile grid before querying, and echoes the snapped values. Distinct anonymous URLs collapse onto a finite cacheable set (ARCH-2).
  • Invalid parameters (unknown bucket, malformed bbox, t1<t0) return 400 with a machine-readable error code - no silent clamping of nonsense.
  • p95 < 150 ms at origin for HOT queries (API-5).

Sub-resources (each independently cacheable): /entity/{slug}/claims?property=mass (full claim history incl. superseded - powers "estimates over time"), /entity/{slug}/related?type=caused_by, /entity/{slug}/contemporaries?limit=50 ("what existed at the same time"), /entity/{slug}/children (part_of tree).

API-3Comparison endpointMVP
GET /api/v1/compare?entities=tyrannosaurus-rex,african-elephant
  → aligned property table: for each shared property_def, both syntheses,
    units converted to canonical, value_type flags (measured vs estimated),
    plus temporal overlap ("did these coexist?" with the overlap computation)

MVP: 2 entities; V2: n entities + chart series.

Tiles and search

API-4Tile and search endpointsMVP
GET /tiles/{layer}/{z}/{x}/{y}.mvt?time={snapped}   -- ARCH-3; layers MVP:
     borders, cities, events, fossils; V2: routes, language, religion...

GET /api/v1/search?q=waterloo&limit=10
  → [{ slug, name, type, t0, t1, thumb, score }]     -- SRCH-1; <50ms p95
GET /api/v1/search?q=...&mode=question               -- V2 NL question, SRCH-3

Cross-cutting contract

API-5Conventions and SLOsMVP
  • All responses: dataset version field; ETag; Cache-Control per endpoint class (viewport/entity: 1h + revalidate; tiles/chunks: immutable, path-versioned).
  • Errors: RFC 7807 problem+json with stable code strings; no 200-with-error-body.
  • Time values on the wire: ISO-8601 where in range; otherwise {"y": -6.6e7} year offsets; one serializer/deserializer shared through generated types.
  • Rate limiting on dynamic endpoints (search, future AI/contributions), not on cacheable GETs.
  • SLOs at origin: viewport p95 < 150 ms; entity p95 < 100 ms; search p95 < 50 ms; tiles p95 < 80 ms.
  • Public API productization (keys, tiers, bulk export) is LATER; but nothing in v1 may leak internal IDs as the only identity - slugs are the public identity.

Shareable URL scheme (frontend routes, server-rendered shells for SEO)

API-6Every view state has a URLMVP
/time/1945-04-30/map/berlin?layers=war,politics      -- date + place view
/time/-66000000/world                                 -- deep time
/entity/tyrannosaurus-rex                             -- entity page
/entity/trex?compare=african-elephant                 -- comparison
/time/1900/records                                    -- V2: records at date
/history/france/1800-1900                             -- V2: generated SEO pages
/inventions/19th-century                              -- V2: generated SEO pages

Rules: URLs are the sharing/education/SEO engine. Canonical entity pages (/entity/{slug}) are server-rendered with meaningful HTML (title, description, key facts, attribution) for crawlers; the app hydrates on top. Generated intersection pages (time × place × category) are V2 and come from the snapshot build job (ARCH-4).
